# Маркетплейс - Архитектура проекта

## Диаграмма С4

Для просмотра диаграммы архитектуры:
```bash
npx likec4 start .likec4
```

### Домены и ответственность

**Основные домены маркетплейса:**
- **User Domain**: Управление пользователями (покупатели и продавцы)
- **Product Domain**: Управление товарным каталогом
- **Order Domain**: Оформление заказов и управление состоянием
- **Payment Domain**: Расчёт и учёт платежей
- **Notification Domain**: Отправка уведомлений о статусах заказов
- **Recommendation Domain**: Персонализированная выдача ленты товаров

### Распределение доменов по сервисам

Каждый домен выделен в отдельный сервис:
- User Service - User Domain
- Product Service - Product Domain
- Order Service - Order Domain
- Payment Service - Payment Domain
- Notification Service - Notification Domain
- Recommendation Service - Recommendation Domain

**Почему выбрано такое разбиение:**

Каждый сервис отвечает за свою область, чтобы:
- Изменения в одном сервисе не ломали другие
- Можно было масштабировать только нужные части системы
- Разные команды могли работать параллельно
- Данные каждого сервиса были изолированы

### Границы владения данными

Каждый сервис владеет своими данными и отвечает за определенную область:

- **User Service**: User Database - управление пользователями, аутентификация, профили
- **Product Service**: Product Database - каталог товаров, категории, цены, наличие
- **Order Service**: Order Database - история заказов, статусы заказов, корзина
- **Payment Service**: Payment Database - транзакции, история платежей, балансы
- **Notification Service**: Notification Database - уведомления, шаблоны сообщений
- **Recommendation Service**: Recommendation Database - модели персонализации, данные о поведении

**Отсутствуют разделяемые базы данных между сервисами** - каждый сервис имеет эксклюзивный доступ к своей БД

**Взаимодействия сервисов:**
- **Синхронное**: REST API через API Gateway (HTTP протокол)
- **Асинхронное**: Message Queue (Kafka/RabbitMQ, AMQP протокол)

**Примеры взаимодействия:**
- Order Service -> User Service: REST запрос для валидации пользователя
- Order Service -> Message Queue: событие создания заказа
- Message Queue -> Notification Service: асинхронная доставка уведомлений
- Order Service/Product Service -> Message Queue: события поведения пользователей
- Message Queue -> Recommendation Service: данные для персонализации
- API Gateway -> Recommendation Service: запросы персонализированных рекомендаций

## Альтернативные варианты архитектурного разбиения

### Вариант 1: Монолитная архитектура
Единое приложение с общей реляционной БД, где все модули работают в одном процессе

**Плюсы:**
- Простота начальной разработки
- Легкое развертывание
- Низкие операционные затраты - меньше серверов и инфры
- Простая отладка - все логи и трассировки в одном месте

**Минусы:**
- Сложность масштабирования - нельзя масштабировать отдельные компоненты
- Высокая связность - изменение в одном модуле требует пересборки всего приложения
- При росте проекта сложно поддерживать чистую архитектуру
- Ограничения для больших команд - сложно работать параллельно над разными функциями

### Вариант 2: Микросервисная архитектура
Разделение на независимые сервисов с отдельными БД, оркестрация через API Gateway

**Плюсы:**
- Независимое масштабирование
- Четкие границы ответственности
- Устойчивость к отказам - падение одного сервиса не ломает все
- Параллельная разработка - разные команды могут работать над разными сервисами
- Технологическая гибкость - возможность использовать разные технологии для разных сервисов

**Минусы:**
- Сложность оркестрации - нужно управлять множеством сервисов
- Выше операционные затраты - больше серверов и инфры
- Сложность распределенных транзакций - обеспечение согласованности данных
- Задержки в разработке - координация между командами требует дополнительного времени

## Почему выбрали микросервисы

1. Каждый сервис имеет свою БД
2. Можно масштабировать отдельные сервисы при росте нагрузки
3. Если один сервис упадет, остальные продолжат работать
4. Разные команды могут работать параллельно

**Trade-off:**
- Сложнее разрабатывать, но проще масштабировать
- Больше серверов, но лучше отказоустойчивость
- Нужна координация команд, но сервисы развиваются независимо

## Инструкция запуска

### Запуск сервиса
```bash
docker-compose up -d user-service
```

### Проверка работы
```bash
curl http://localhost:8001/health
```

## Техническая реализация

- **Стек**: Python/FastAPI, PostgreSQL, Docker
- **Архитектура**: Микросервисная архитектура с API Gateway
- **Коммуникация**: REST API + Message Queue для асинхронных операций
